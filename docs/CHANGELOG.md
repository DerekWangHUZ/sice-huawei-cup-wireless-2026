## [2026-10-18] 掉电固化（配置 Flash）+ 数码管改为实时遥测读数

> **协议 §4.3 / §4.5 / §4.8 修订**：复用 `SET_STATE` 自定稿起即为保留的 `p2`
> （16 位）传递实时合加速度，帧长、命令码、校验规则一律不变。S3 侧需重编重烧
> 才能看到实时读数——未升级的 S3 只在状态边沿发 `p2=0x0000`，数码管会先显示
> `00.00`、3s 后因停止刷新而老化成 `----`（功能不回退，只是没有读数）。

### 变更内容

**问题一：重新上电后配置丢失**

原链路只有 `program_bit.tcl`（JTAG 写 FPGA SRAM），**断电即失**——每次上电都要
重烧一次。板载 Micron N25Q32 配置 Flash 一直在，缺的只是"把 `top.mcs`
写进去"这一步。

FPGA（`firmware/coprocessor`）：

- **新增 `program_mcs.tcl`**：无头把 `top.mcs` 烧进板载配置 Flash，与
  `program_bit.tcl` 同构（同样的 `xc7a35t` 器件型号护栏），并额外：
  显式指定存储器件 `n25q32-3.3v-spi-x1_x2_x4`（与 `gen_mcs.tcl` 的
  `-size 32 / SPIx1` 对应），开启 ERASE/PROGRAM/VERIFY、关闭 BLANK_CHECK，
  打印 `MCS_PROGRAM_OK`。缺 mcs 报 `MCS_MISSING`、器件不匹配报
  `CFGMEM_PART_MISSING`。
  脚本内会自动定位并加载 Vivado 自带的 SPI 桥接位流（JTAG 间接访问 Flash 的
  必要前置步骤，GUI 会自动做、手写 Tcl 容易漏）。
- 改完 RTL 必须重跑 `gen_mcs.tcl` + `program_mcs.tcl`，否则 Flash 里仍是旧
  比特流。`program_bit.tcl` 保留为"改完立刻看现象"的临时手段。
- **`pins.xdc` 补 `CFGBVS` / `CONFIG_VOLTAGE`**：消除 DRC 的 `CFGBVS-1`
  告警，明确配置 bank 为 3.3V。
- ⚠️ **固化已成功，但上电仍不会自动启动**——需按一次板上 CONFIG 按钮，
  详见本条目末尾"未覆盖 / 已知问题"。
- `docs/Vivado工程移植方案.md` 补目录项与固化小节。

**问题二：数码管"看不懂 + 浪费位数"**

原显示只用了 6 位中的 2 位（`S0`），告警时还有两位是固定的 `--`；观众看不出
数字含义。实测反馈："显示数字是什么意思？要让人明白，并且不要只是显示几个
固定的数字/字母，这样太浪费数码管了。"

- **`rtl/seg_display.v` 重写为「2 位状态助记符 + 4 位实时合加速度读数」**：

  | 位 | 内容 |
  |---|---|
  | `an[5]` `an[4]` | 状态助记符：`St` 静止 / `Go` 走动 / `Pd` 待确认 / `AL` 告警 |
  | `an[3]`~`an[0]` | 合加速度 "XX.XX"，单位 g，`an[2]` 的 dp 作小数点 |

  例：静止 `St01.00`，走动 `Go01.24`，冲击 `Pd03.40`，告警 `AL03.40`。
  6 位全部承载信息，且读数随运动实时变化——既是信息也是存活指示。
- **段码表补齐**：原表只有 `0/1/2/3/F/A/L/S/-/空`，现补 `4~9`、`t`、`o`、`G`、
  `P`、`d`。
- **取消小数点"流水点"动画**：`dp` 现在承担小数点语义，与流水动画冲突；
  告警的整屏 3.3Hz 急闪、待确认的 4Hz 快闪保留（快闪对象改为助记符 2 位，
  读数位保持稳定可读）。
- **`rtl/cmd_decoder.v` 新增 `mag_x100[15:0]` / `mag_valid` / `mag_update`**：在
  `SET_STATE` 分支锁存 `p2`（`{n5,n4}` 小端）。`p2 == 0xFFFF` 为"暂无有效遥测"
  哨兵，此时读数位显示 `----` —— **绝不显示一个假的 `00.00`**。
- **FPGA 侧遥测 3s 老化看门狗（`TELEM_STALE_DIV`）**：`SEG_DISPLAY` 自己计时，
  超过 3s 没收到有效遥测就把读数切成 `----`。这是本轮排查中发现的必要补强：
  实测该 IDF 构建下 S3 的 `SO_RCVTIMEO` 不生效，收包任务在无数据时**阻塞在
  `recvfrom` 上**，因此"S3 主动发哨兵"这条路径在数据彻底停摆时并不可靠
  （详见"决策依据"第 6 条）。老化放 FPGA 侧后，读数真实性不再依赖 S3 行为，
  并且在 testbench 里可精确断言。
  **告警期间老化计时器冻结**：契约 §4.5 第 2 条要求确认跌倒后不再发 `SET_STATE`，
  若仍按 3s 老化，告警画面的读数会在 3s 后变成 `----`——那不符合设计意图。
  冻结后读数定格为冲击幅值直到告警解除（testbench 已加断言，观察窗口 3ms
  远超测试用 2ms 阈值，确认 `mag_fresh` 保持为 1）。
- `rtl/top.v` 增加两路连线；`sim/tb_top.v` 改为按位快照捕获 6 位字形组合，
  新增遥测读数（`01.02`/`03.40`）、哨兵 `----`、助记符 `St/Go/Pd/AL` 断言，
  取代原先针对 `FALL--` 的零散字形断言。

基站（`firmware/base_station`）：

- **`main/fall_core.c` 新增 `fall_acc_mag_centi_g()`**：把三轴原始 ADC 值换算成
  0.01g 单位的合加速度幅值。**纯整数逐位开方实现**，不引入 `math.h`——该文件
  必须保持纯 C99，因为离线自测宿主程序直接 `#include` 它（纪律见
  `tools/offline_test/test_harness.c` 文件头）。
- **`main/fpga_link.c` 新增 `fpga_link_send_state_telemetry()`**：`SET_STATE`
  携带遥测；周期刷新帧走 `fpga_link_send_cmd_ex(..., verbose=false)`，日志降到
  DEBUG，避免 1Hz 刷屏。新增 `FPGA_TEL_NO_DATA = 0xFFFF` 哨兵常量。
- **`main/base_station.c`**：新增 `FPGA_TEL_PERIOD_MS = 1000u` 与
  `fpga_telemetry_tick()`，1Hz 重发遥测刷新帧，并遵守两条约束：
  ① `CONFIRMED` 期间停发（保持"确认跌倒后只发 ALARM"的既有语义，同时让告警
  画面上的读数**定格为冲击幅值**，正好是最有信息量的数字）；
  ② 数据流掉线（`DATA_TIMEOUT_MS`）时发 `0xFFFF` 哨兵而非上一帧读数。
  上电首帧同步改为 `SET_STATE(0, 0xFFFF)`。
  状态变化沿的下发也改携带当前幅值，避免读数滞后一次刷新。

### 决策依据

1. **为什么复用 `p2` 而不是新增命令码**：`p2` 自协议定稿起就是保留位，所有
   发送方一律填 `0x0000`，`cmd_decoder.v` 早已解出 `n4`/`n5` 却完全忽略。
   复用它不新增命令码、不改帧长与校验规则，且 FPGA 对重复 `SET_STATE` 完全
   幂等（只做锁存、不触发动作），因此周期刷新不产生副作用。新增命令码则要
   同时改 §4.3 表、白名单、S3 与 FPGA 两侧，收益相同而风险更大。
2. **为什么用 0xFFFF 作哨兵**：int16 输入下合加速度的理论上限是
   `isqrt(3*32767²) = 56754` LSB → `2771`（27.71g），**永远到不了 65535**，
   所以哨兵与合法值不可能混淆（离线自测场景 15 把这一点连同各换算点一起钉死）。
3. **为什么告警期间停发遥测**：契约 §4.5 第 2 条明确"确认跌倒后只发 ALARM，
   不发 SET_STATE(3)"。停发同时满足该条与"读数定格在冲击幅值"的显示需求，
   一个约束解决两个问题。
4. **被否决的方案**：纯本地动画（用 FPGA 本地计时器/计数器凑数字）——计数器
   不是信息，仍属"固定的数字"，达不到用户诉求；保留 `FALL` 文字——占 4 位只剩
   2 位给数值，精度不足且仍浪费。
5. **固化失败可恢复**：`program_mcs.tcl` 只在显式指定器件、且 mcs 存在时动作；
   烧写失败不影响 JTAG 可用性，随时可用 `program_bit.tcl` 恢复现场。
   注意：板卡若被跳线设为 JTAG 启动模式，上电不会从 Flash 加载（属上机首查项，
   见 `docs/FPGA实验板资料参考.md`）。
6. **为什么遥测老化放在 FPGA 侧（本轮排查发现的新问题）**：`base_station.c`
   给收包 socket 设了 100ms `SO_RCVTIMEO`，用于"数据停摆时也要跑
   `fall_detector_tick`"。实机验证发现**该超时在本 IDF 构建下不生效**：
   断电重启后连续观察 25s（PowerShell 直读串口 + `idf.py monitor` 两种方式），
   日志停在 `main_task: Returned from app_main()`，`STATS` 一次都没打印；
   而同一份日志在"有帧到达"时会正常打印 `STATS`。这与历史实测记录
   （"两场景间 33s 无数据，**收到下一帧时**才判 WALK→IDLE"）完全吻合——
   即空闲路径从来只在被数据唤醒时才跑。
   曾用 `select()` 显式 100ms 超时替代 `SO_RCVTIMEO` 重新编译烧写，实机表现
   相同（仍无 `STATS`），因**无法在无数据场景下取得可验证的改善**而回退，
   以免改动已实测通过的主链路。这条属于既有缺陷、与本次两个需求正交，
   已如实记录待后续单独排查（记录见 `base_station.c` 内的注释）。
   对策：把"读数不能过期"的责任放到 FPGA 侧（第 2 条的 3s 老化），
   这样即使 S3 空闲路径不工作，显示也不会骗人。

### 验收证据

- FPGA 无头仿真：`SIM RESULT: PASS`，含新增的遥测读数、哨兵、3s 老化看门狗、
  助记符断言，以及"告警期间读数不老化"断言（老化场景用
  `defparam TELEM_STALE_DIV=100000` 缩短到 2ms 验证——该值必须显著大于
  一帧 UART 传输时间 ~700us，否则连续两帧之间就会老化，测到的不是设计行为；
  断言流程"帧后 200us 仍新鲜 → 3ms 后变 `----` → 再发一帧又恢复"）。
- Vivado 无头综合/实现/比特流：`BITSTREAM_OK`，DRC 0 Errors，
  `All user specified timing constraints are met`，
  833 LUT（4.00%）/ 488 FF（1.17%）/ 35 IOB（20.59%）。
  （LUT 从上一版的 627 涨到 833，主要来自 16 位十进制拆分所需的常数除法。）
- `gen_mcs.tcl` → `MCS_OK`，`top.mcs` 6,165,628 B。
- 基站固件：`idf.py build` 全量重编 **0 error / 0 编译告警**，
  `base_station.bin` = 930,192 B（1M 分区余 11%）。
- 离线自测：**15/15**（新增场景 15 逐点锁定 `fall_acc_mag_centi_g` 换算与哨兵无歧义）。
- 上板：`program_bit.tcl` → `PROGRAM_OK` + `End of startup status: HIGH`；

### 未覆盖 / 已知问题（需上机）

- **固化后的上电自动启动：目前无法修复，记录如下。**

  Flash 烧写本身是成功的：`Erase Operation successful` /
  `Program/Verify Operation successful`，读回内容与写入的 `top.mcs`
  逐字节一致。

  但**断电再上电时板子不会自动启动**（`DONE` 保持 0，数码管/LED/蜂鸣器
  全无反应）；**手动按一下板上 CONFIG 按钮，立即正常启动**。

  这个现象本身就排除了一大类可能——按下 CONFIG 能起来，说明 Flash 内容
  正确、MSEL 已处于 Master SPI、烧写方式无误、mcs 格式无误（与 Vivado 自带
  样例 `ac701_test.mcs` 结构一致）。**唯一失效的是"上电瞬间的自动触发"**。
  CONFIG 按钮接的是 `PROGRAM_B`（低有效配置复位），它能手动生效而上电不
  生效，指向板级上电复位电路/电源上升沿问题。

  已尝试且无效：XDC 中设置 `BITSTREAM.CONFIG.PROGPIN/INITPIN/DONEPIN =
  Pull-up`（用 FPGA 内部弱上拉替代板上外部上拉）——实测仍必须按 CONFIG，
  已回退该改动。

  **历史事实：该板在本次改动之前无需按 CONFIG，上电即自动启动。**
  本次所有改动均未触及配置电路相关约束（`pins.xdc` 引脚分配、
  `gen_mcs.tcl`、比特流生成参数均未改变），**但无法定位具体致因**。

  详见 `docs/FPGA实验板资料参考.md` §9b 的"已知问题"小节。
  当前绕过方式：上电后按一次 CONFIG（已验证有效），或用 `program_bit.tcl`
  经 JTAG 下载（需电脑）。

- 另需说明：`program_mcs.tcl` 的开发过程走过弯路——早期一直报

  GUI 会自动完成这一步，手写 Tcl 不会。脚本现已内置该步骤，

### 决策依据

- **音量不足的根因是驱动方式，不是代码参数**：原实现只有 2Hz 通断。对**无源**蜂鸣器
  那只是轻微"咔哒"声，必须在共鸣频率（约 2.7kHz）驱动才有正常声压。板卡资料里蜂鸣器
  引脚取自**电子琴实验** XDC —— 电子琴要求能播放不同音高，强烈指向无源器件，与原注释
  "本期板载为有源"存疑。故保留 `TONE_ENABLE` 开关：默认叠加载波，若实板确为有源且叠加
  后音色变差，置 0 即回到干净通断——一处参数即可回退。
- **节拍改"三短一停"**：恒定 2Hz 通断在现场辨识度低；三短一停更接近真实报警器听感，
  且与 LED 爆闪共用同一 `beat` 包络，声音与光天然同步，无需额外同步逻辑。
- **LED 走软 PWM 而非纯通断**：呼吸灯必须有亮度维度。16 路 8 位 PWM（约 195kHz 帧率）
  在本设计只占 627 LUT / 509 FF（3.0% / 1.2%），代价可忽略。

## [2026-10-18] 判定算法对照文献评审：确认窗口修订 + 姿态门钩子

对照业界同类实现评审跌倒判定（触发本次修订的证据）：

- **KFall 数据集 ESP32+MPU-6050 项目**（github.com/MadlyFriese/esp32-fall-detector，
  线性 SVM + 冲击门限双证据，fall recall 0.954）：
  门限扫描 gate=3.0g 时 fall recall 仅 0.827、gate=1.7g 时 0.896；原文点名
  magnitude-only 的头号误报 "sitting down heavily sails past it"；其
  "活动上下文 + 物理冲击"双证据互证思路与本工程"冲击 + 静止"结构一致。
- **学术阈值法**：Kepski & Kwolek (IET 2017) 以 SV_total > 2.5g 判冲击；
  三段式框架（活动强度 / 姿态 / 转移分析）中本工程缺"姿态分析"一环。

### 修订 1（P0）：PENDING 确认改"持续静止计时 + 观察上限"

旧实现是快照式——只在冲击后恰满 STILL_WINDOW_MS(1.5s) 的那一帧检查是否
静止，存在两条漏报路径：

1. 躺稳后在到期帧恰逢抽动（gyro > 50°/s）→ 退出 PENDING，此后无新冲击不再触发；
2. 倒地后持续挪动超过 1.5s 才静止 → 错过唯一确认时刻。

新实现：持续静止（gyro_quiet && acc_near_g）累计满 STILL_WINDOW_MS 即确认
（被运动打断则计时清零重来）；冲击后 PENDING_MAX_MS(4s，新增宏) 内仍未
确认则按非跌倒退出。上限同时防"碰撞后走动再坐下"被误确认（到期时坐下
静止不足 1.5s）。残余风险（已知并接受）：冲击后 1.5~4s 才坐下静止仍会
误报，由修订 2 根治。

### 修订 2（P1）：姿态门钩子（默认关闭）

`POSTURE_CHECK_ENABLE=0`（fall_core.h）。开启后确认前额外要求：确认时刻
重力方向与"竖直参考"夹角 >60°（躺平）。竖直参考在 IDLE 持续静止 2s 后
自动校准；未校准 fail-open（行为与门关闭完全一致）。整数 Q4 定点实现
（dot²·16 < a2·ref2·cos²θ·16），无浮点无 math.h，溢出有界（函数注释有
分析）。⚠️ 前提是佩戴朝向固定——待成员 B 确定佩戴位置（胸口/腰部 vs
手臂）后再开启。

### 修订 3（P2）：阈值依据回写

IMPACT_THRESH_G 保持 3.0g（演示期压误报优先），头文件注释补 2.5g 学术
基准与 KFall 扫描数据；调参指引交成员 C：拿 SD 卡 CSV 对真实动作做阈值
扫描（文献数据支持在实测基础上向 2.0~2.5g 下调）。

### 回归证据

- 离线自测 11 -> 14 场景全过（`tools/offline_test/logs/offline_test.log`）：
  - 新增 [12] fall_late_still：冲击后挪动 2.2s 才静止 → 确认（旧逻辑漏报）；
  - 新增 [13] fall_boundary_twitch：到期帧恰逢抽动 → 确认（旧逻辑漏报）；
  - 新增 [14] bump_walk_sit：碰撞后走动 3.2s 再坐下 → 不报警（上限防误报回归）；

### 决策依据

- **"不回归"的判据是哪些值必须吻合**：冲击帧号与 `mag2`、确认帧号、确认时间窗、
  以及 ALARM/CLEAR 下行帧的逐字节内容。这些是决定告警正确性与 FPGA 能否正确解码的量，
  它们吻合才叫"没回归"；`STATS` 计数只作辅助。
- **离线自测与真机的时间戳口径差异（重要，勿误"修"）**：离线 harness 在解析完一帧后
  才 `now_ms += dt`（第 0 帧记为 t=20ms），真机用帧到达时的 `esp_timer` 时刻，
  因此所有**基于时间的阈值**（如 `MOTION_HOLD_MS=300ms`）在真机上恰好早一帧闭合
  （15 帧 × 20ms = 300ms → `seq=15` 而非 16）。表现为 `seq` 与随之变化的 `mag2` 差 1 帧，
  而 `gyro2` 一致。**这是两侧时间戳约定不同，不是缺陷**，不要为此改动判定逻辑。



- **FatFs 不支持 exFAT 是硬约束**：IDF v6.1 的 `ffconf.h` 中 `#define FF_FS_EXFAT 0` 写死、
  无对应 Kconfig。将来若 C 侧要求大容量卡，只能选 FAT32（MBR），不能指望开 exFAT。

### 决策依据

- **不用 IDF 内置 SSD1306 驱动（重要）**：`esp_lcd_panel_ssd1306` 的 `draw_bitmap`
  依赖 `0x21/0x22`（设置列/页范围）——那是 SSD1306 的**水平寻址**命令，
  **SH1106 不支持**。而 1.3" 四脚模块两种控制器都常见（本机到货型号待上板确认）。
  故自写约 250 行精简驱动，统一走**页寻址**（`0xB0|page` + 列地址半字节），
  两种控制器一套代码，差异只在初始化序列的电荷泵命令与列偏移
  （`OLED_CTRL_SH1106` 宏切换）。这样既不赌模块型号，也不引入新组件依赖。
- **写卡必须离开收包任务**：SPI+FATFS 单次写卡可达数十至上百毫秒，若在 50Hz
  收包任务里 `f_write`，会打乱 `SO_RCVTIMEO` 100ms 节拍与 `fall_detector_tick`，
  直接破坏已验证的判定时序。故采用**环形缓冲 + 独立低优先级任务**：
  生产者 `xRingbufferSend` 超时 0（绝不阻塞），队列满即丢并计 `DROP`。
- **CSV 格式抽成纯 C99 模块**：与 `fall_core` 同一纪律——能被宿主机离线自测
  编译断言"文档写的 = 固件写的"，杜绝接口漂移。`log_fmt.c` 只依赖 stdint/stddef/stdio。
- **六轴写原始 int16 而非浮点**：契约 §1.2 空口传的就是原始 ADC 值，落盘保持无损；
  浮点换算交代换常数（2048 LSB/g、16.384 LSB/°/s）留给 C 侧，也免去 MCU 浮点格式化开销。
- **`State` 列订正为 4 值**：原 §2.1 写 3 值（`2=跌倒`）与 §4.3 的 4 状态码矛盾，
  会把 `FALL_PENDING` 误读成"已跌倒"。以 §4.3 为准统一。**跨团队影响：成员 C
  若已按 3 值写解析脚本需同步更新。**
- **容错一律"降级不阻断"**：SD 挂载失败、OLED 无应答、写卡中途失败，都只禁用该功能
  并打日志，判定与声光报警主链路完全不受影响（与 `fpga_link` 失败同策略）。
- **上机操作内容不入库（沿用既有规范）**：仓库只放**接线与引脚事实**（契约 §5.1 要求的

- **实测修正 3（告警解除语义，重要）**：
  - 初版为 `ALARM_HOLD` 定时 10s 解除——人躺地上昏迷时穿戴端仍推流
    （静止特征），10s 一到报警自停，人还在地上报警器却闭嘴，语义错误；
  - 第一轮修补（无帧 tick 兜底）又被 3s 掉线保护提前掐断告警（实测
    "刚发就报警结束了"）；
  - **最终语义：告警为锁存，唯一解除判据 = 持续起身活动**
    （角速度 > GETUP_GYRO_DPS 持续 GETUP_HOLD_MS，对齐 fall_recover
    的"爬起"判据）。数据停摆时告警保持——人昏迷 + 设备故障恰是最
    需要报警的时刻。`fall_detector_tick()` 保留，仅负责非告警态掉线保护。
- **离线自测扩到 8 场景**：新增"停摆保持告警"与"起身解除"（fall_getup
  场景，自带爬起段 700ms）两个回归测试；演示剧本一条命令完成
  "走动→摔倒→报警→被扶起"。
- **FPGA 上电自检（POST）**：上电 2s 强制告警显示（FALL-- 闪烁 + 蜂鸣 +
  LED 全亮）后自动待机，单板验证声光链路，契约 §4.7。

### 决策依据

- 告警解除的三次迭代教训：**解除判据必须是物理事件（人起来了），
  不能是时间**。定时解除在"人昏迷躺地"这一最需要报警的场景下失效；
  掉线解除在"演示停发数据"场景下把告警掐成 1~3 秒。锁存 + 起身判据
  是跌倒报警器的标准语义。
- 引脚勘误流程：实板照片核对排针丝印（B15/C14/D14... 与 A2/B1/G2...），
  确认 F12/F13 未引出，勘误写回参考文档防止后人重蹈。

### 已知事项

  fall_getup 解除告警再继续。

## [2026-10-14] 撤除 STM32 协处理器，基站改为 S3 + FPGA 双板架构

### 变更内容

- 删除 `firmware/coprocessors/stm32/` 整个 STM32F401RE 工程（CubeMX 工程 + CMSIS/HAL 驱动 + 启动文件 + 链接脚本）。
- `firmware/coprocessors/` 目录更名为 `firmware/coprocessor/`，仅保留 Artix-7 FPGA 工程。
- FPGA 工程由 `fpga` 重建为 `coprocessor`，源码内容（`top.v`、`pins.xdc`）与原工程逐字一致，仅工程名与路径变化。
- 全仓库文档中 STM32 相关表述同步清除，`README.md` 硬件拓扑描述同步更新。

### 决策依据

撤除 STM32 不是因为"不好用"或"做不出来"，而是因为在系统既定架构下，**STM32 找不到任何技术上不可替代的职责**。逐项排查结论如下：

| 候选角色 | 结论 |
|---|---|
| 姿态解算 | **数据第二落点，结构性多余。** MPU6050 长在穿戴端，姿态数据经 WiFi/UDP 进入系统的第一接收者必然是 ESP32-S3。STM32 若要参与，只能由 S3 经 UART 转手，形成"穿戴端 → S3 → STM32 → 解算 → S3"的环路。且 F401RE @84MHz 单核的滤波算力开销本身极小，S3 双核 240MHz 做同一件事更轻松，卸载无收益。 |
| 报警执行（蜂鸣器/继电器/指示灯） | **与 FPGA 板全面重叠且劣势。** NUCLEO-F401RE 板载输出资源仅 1 颗用户 LED（PA5）；FPGA 实验板有 16 颗 LED + 板载蜂鸣器 + 6 位七段数码管 + 8 位 DAC。告警表达 FPGA 板占绝对优势，且无需外接模块。 |
| SD 卡数据记录 / OLED 驱动 | S3 经 SPI/I2C 直接驱动均为标准做法；经 UART 转给 STM32 再操作纯属增加故障点。 |
| CSI 特征卸载计算 | **CSI 产生于 S3 的 WiFi 外设内部**，任何卸载都必须先把数据搬出 S3，搬运成本高于算力节省。 |
| 协议桥接（S3↔FPGA 中转） | 两者均为 3.3V UART，可直接对接，中间加一块板纯增故障点。 |
| 看门狗 / 系统健康监控 | 技术成立，但 S3 自带 Task WDT + RTC WDT，对本项目 3 分钟演示场景零收益。 |
| FPGA 比特流加载（MCU 经 SPI 配置） | 技术成立，但 JTAG 下载已验证可用，零演示收益且需额外接线与比特流存储。 |
| 双通道冗余判决 | **伪冗余。** STM32 与 S3 读取同一份源自 S3 的数据，数据错误时两者会一起错；真冗余需要接入独立传感器，与项目"废除外置独立信标"的前提冲突。 |
| 接入本地有线传感器构成"WiFi 无线感知 + 有线本地感知"双通道 | 唯一非二道贩子式的角色，但**直接破坏项目核心卖点**（README：废除外置独立信标，复用 UDP 报文作为空间多径激励源），且需追加硬件采购。 |

补充一点常被用来支持此类协处理器的论点："裸机执行确定性好，不受 WiFi 协议栈抖动影响"。该论点本身成立，但本项目的跌倒判据是"合加速度冲击阈值 + 静止窗口"，UDP 包抵达 S3 后即可立即判定，**不存在需要确定性硬实时环的处理环节**，故该论点不适用于本系统。

### 影响

- 系统仍是**三处理器异构**：ESP32-S3（感知主控 + 网络中枢）、Artix-7 FPGA（硬件级并行声光告警）、ESP32-CAM（穿戴端抓拍节点）。变化在于**基站桌面由三块板减为两块**，"多层次异构边缘协同"的论述不受影响，且每一级的分工更清晰。
- ⚠️ **跨团队影响**：成员 C 正在按"三处理器/三块板"撰写《作品设计报告》，需同步修改相关表述。
- 演示桌上减少一块板、一条 ST-Link 线、一组会松的杜邦线，现场稳定性提升。

## [2026-10-14] FPGA 工程重建，`.xpr` 不再纳入版本控制

### 变更内容

- FPGA 工程由 `firmware/coprocessors/fpga/`（工程名 `fpga`）重建为 `firmware/coprocessor/`（工程名 `coprocessor`）。
- `.gitignore` 新增 `*.xpr`，Vivado 工程文件不再入库。

### 决策依据

`.xpr` 是 Vivado 的**工程状态快照**而非工程定义，其内部写死绝对路径。实测（Vivado 2026.1）将 `.xpr` 与源码复制到新路径后打开：工程"能打开"、综合能跑完，但**文件列表解析不可靠**——源码目录含 2 个文件，工程只认到 1 个，存在约束文件未加载却综合通过的隐患。

改为只纳入源码（`top.v`、`pins.xdc`）后，工程可在任意机器上由导出脚本重建。

### 补充：手写 glob 自动发现脚本方案已否决

曾提出用 `glob` 自动扫描源文件以"加文件即生效、脚本永不改"，实测证伪：

- `glob ... ** *.v` 在本机 Vivado 2026.1 的 Tcl 环境下**不递归**，子目录内文件被静默漏掉，综合报 `module 'nested' not found`
- 文件类型会扩展（`.vhd`/`.vh`/`.sv`/`.xci`/`.bd`），每次扩展都要改脚本，漏改后果是静默失败
- `add_files` 不设置 file_type 属性会退回默认值，`.vh` 头文件、`.xdc` 约束、VHDL 2008 开关等专门属性会丢失

改用 Vivado 官方 `write_project_tcl` 导出重建脚本，实测换路径 + `--origin_dir` 覆盖后，源文件与约束文件均正确加载、综合 0 error。完整方案见 [Vivado工程移植方案.md](Vivado工程移植方案.md)。
